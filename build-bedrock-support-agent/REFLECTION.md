# Reflection

I chose to store the original customer query separately from the context retrieved by the memory hook. Before responding, the hook adds actor-scoped facts and preferences to the model's input; after responding, it saves the clean user and assistant exchange. This prevents previously retrieved memories from being repeatedly persisted as new customer statements. Session history and long-term preferences have distinct roles: history supports follow-up questions, while semantic and preference retrieval supports a fresh session. The live tests recalled Jane's name and preference for concise replies across different session identifiers.

One challenge was that successful tool execution did not guarantee a fully grounded answer. In the first deployed refund test, the Lambda returned an approval, but the agent added an unsupported claim that no return label was needed. I retained that capture, tightened the system instruction to separate refund approval from physical-return policy, and validated the corrected response against the tool audit. The browser integration also required attention: the high-level wrapper timed out in the deployed runtime. I retained the required AgentCoreBrowser tool and isolated its Playwright event loop in a dedicated worker, with bounded waits and explicit remote-session cleanup. Local tests verify that the actual SDK tool is registered and that remote resources are released even when connection setup fails.

For production, financial authorization must be enforced outside the language model. The course Gateway has no inbound authentication, and its refund Lambda is a fictional fixture without durable transaction records. A real service should derive customer identity from verified claims, enforce ownership in the backend, and use persistent idempotency keys. Memory also needs deletion controls and personal-data redaction. Finally, infrastructure choices must respect the operating budget: I used S3 Vectors for the Bedrock Knowledge Base after OpenSearch provisioning was rejected for ongoing cost risk. A budget tracker is not a hard spending cap, so usage monitoring and complete resource cleanup remain operational responsibilities.
